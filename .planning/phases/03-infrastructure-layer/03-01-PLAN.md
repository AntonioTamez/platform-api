<objective>
Create the PersonsAPI.Infrastructure project and implement the EF Core InMemory persistence adapter: PersonDbContext, PersonEntityConfiguration (with builder.Ignore(p => p.Age)), PersonRepository implementing IPersonRepository one-to-one, and AddInfrastructure() DI registration. This plan satisfies INFRA-01 (EF Core InMemory provider is the persistence adapter) and lays the foundation that Plan 02 (DataSeeder) and Plan 03 (repository tests) depend on.

Purpose: The Infrastructure layer is the secondary adapter in Hexagonal Architecture. It implements the secondary port (IPersonRepository) defined in Phase 2's Application layer using EF Core InMemory. The critical correctness gate is builder.Ignore(p => p.Age) — without it, EF Core will attempt to map the getter-only computed Age property and either silently create a shadow property or throw at model-building time.

Output: A compilable PersonsAPI.Infrastructure project added to PersonsAPI.sln, containing the four production source files plus the AddInfrastructure DI extension. No tests in this plan (Plan 03 covers tests). No DataSeeder in this plan (Plan 02 covers seeder).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Application → Infrastructure | Application code depends on IPersonRepository (port). Infrastructure must not leak its EF concrete types (PersonDbContext) back across this boundary. |
| Domain → Infrastructure | Domain entities must remain pure POCOs. Infrastructure must not require Domain to know about EF Core. |
| DI root → scoped consumers | PersonDbContext is registered scoped; resolving it from the root provider is forbidden. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-01 | Tampering | PersonRepository — return type | mitigate | GetAllAsync returns `IReadOnlyList<Person>` (not `IQueryable<Person>`). Callers cannot compose LINQ to mutate persisted state or bypass repository methods. Acceptance criterion enforces no `IQueryable<Person>` return signature. |
| T-03-02 | Tampering | PersonEntityConfiguration — Age mapping | mitigate | `builder.Ignore(p => p.Age)` prevents EF from creating a shadow column for Age; client cannot tamper with stored age (it does not exist). Mass-assignment via tracked entity is prevented because Person has no public setters — Application handlers use domain update methods (UpdateName, UpdateDateOfBirth). |
| T-03-03 | Information Disclosure | PersonDbContext exposure | mitigate | PersonDbContext lives in `PersonsAPI.Infrastructure.Persistence` namespace, only the Infrastructure project. Application project does not (and cannot) reference Infrastructure — dependency flows one-way. Project topology enforces non-exposure at compile time. |
| T-03-04 | Denial of Service | Unbounded GetAllAsync | accept | InMemory provider with 3 seeded persons; no real network or disk; v1 has no pagination requirement (out of scope per REQUIREMENTS.md). Documented for v2 (PERS-01 SQL migration would add pagination). |
| T-03-SC | Tampering | NuGet package install (Microsoft.EntityFrameworkCore.InMemory 10.0.8) | mitigate | First-party Microsoft package, [VERIFIED nuget.org] in RESEARCH.md Package Legitimacy Audit. slopcheck does not cover NuGet; package is the same major version (10.0.x) used by Domain.Tests/Application.Tests test infrastructure ecosystem. No human checkpoint required (not ASSUMED/SUS). |
| T-03-05 | Elevation of Privilege | Scoped DbContext leak | mitigate | DI registration uses `AddDbContext<PersonDbContext>` (scoped by default) and `AddScoped<IPersonRepository, PersonRepository>()`. Plan 02's DataSeeder creates its own scope (`services.CreateScope()`) before resolving the context — prevents the root-provider exception (RESEARCH.md Pitfall 4). |
</threat_model>
