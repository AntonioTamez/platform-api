| caller → Person.Create()/Update*() | Untrusted field values cross here; guard clauses are the validation boundary |
| EF Core → protected Person() | Phase-3 materialization path; must not run validation or it throws on valid persisted data |
| (no runtime boundary) | Pure C# library; no HTTP, network, persistence, or serialization surface in this phase |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-04 | Tampering | Name fields via Create()/UpdateName() | mitigate | ValidateName() rejects null/empty/whitespace, <2, >100 with DomainException; tests assert all three branches on all three fields (ASVS V5 input validation at the domain boundary) |
| T-01-05 | Tampering | DateOfBirth via Create()/UpdateDateOfBirth() | mitigate | ValidateDateOfBirth() rejects future dates and dates >150 years past; the 150-year cap also bounds the Age computation input (prevents absurd values) |
| T-01-06 | Tampering / EoP | Invariant bypass via property setters | mitigate | All properties are `private set`, no public constructor; reflection test `Person_HasNoPublicPropertySetters` asserts no public setter exists so callers cannot construct an invalid Person |
| T-01-07 | Tampering | Invariant bypass via EF protected constructor | mitigate | `protected Person()` is empty (no validation, Pitfall 4); Create()/Update* are the only public mutation paths — the protected ctor is not callable from application code |
| T-01-08 | Denial of service | Age integer arithmetic on extreme dates | mitigate | 150-year past cap and future-date rejection bound DateOfBirth.Year so `today.Year - DateOfBirth.Year` cannot overflow Int32; no unbounded input reaches the computation |
| T-01-09 | Information disclosure | DomainException messages | accept | Messages name the violated field/rule in English only (D-04); no PII, secrets, or stack internals exposed — accepted for a no-PII learning domain |
