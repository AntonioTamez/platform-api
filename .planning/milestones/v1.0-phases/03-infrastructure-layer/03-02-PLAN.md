<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Startup (root IServiceProvider) → scoped PersonDbContext | Resolving a scoped service from the root provider throws by default; DataSeeder must cross this boundary by creating its own scope. |
| DataSeeder → Person factory | Seed data flows through Person.Create(), enforcing domain invariants (name length, DOB range). Bad seed data fails at the Domain boundary, not at EF. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-06 | Tampering | Seed data invariants | mitigate | DataSeeder uses `Person.Create(...)` factory (not `new Person { ... }`). All three seed records pass Domain ValidateName + ValidateDateOfBirth gates. If a future edit introduces a malformed name or future-dated DOB, `Person.Create` throws DomainException at startup — fail-fast. |
| T-03-07 | Denial of Service | Seeder duplication on repeated startup | mitigate | Idempotency guard `if (context.Persons.Any()) return;` (D-05) ensures repeat startups do not multiply rows. Even though InMemory resets per process, the guard teaches the production-safe pattern and prevents test-harness duplicate inserts. |
| T-03-08 | Elevation of Privilege | Scoped service resolution from root | mitigate | `services.CreateScope()` + `using` (D-04). Resolving PersonDbContext from `app.Services` directly would throw `Cannot resolve scoped service 'PersonDbContext' from root provider` — the explicit scope prevents this entire class of bug (RESEARCH.md Pitfall 4). |
| T-03-09 | Information Disclosure | Seed PII | accept | Seed names are fictional (María García López, Carlos Ramírez Martínez, Ana Flores Mendoza). No real-world PII; learning project; out-of-scope items per REQUIREMENTS.md confirm no authentication or data protection requirements in v1. |
</threat_model>
